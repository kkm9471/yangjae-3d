# 어떻게 만들었나

> 이 문서는 코드를 못 읽어도 **무엇이 어떻게 돌아가는지** 알 수 있게 쓴 것입니다.
> 나중에 "왜 이렇게 했더라"를 되짚을 때 보세요.

---

## 큰 그림 — 세 단계

```
   ①  OpenStreetMap        ②  파이썬                    ③  브라우저
   ┌──────────────┐        ┌──────────────────┐        ┌────────────────────┐
   │ 전 세계 지도  │  1회   │ 위경도 → 미터     │  파일  │ 상자를 세우고       │
   │ (무료·공개)   │ ─────▶ │ 건물 외곽선·높이  │ ─────▶ │ 창문·간판을 그리고  │
   │              │  요청  │ 도로 중심선·폭    │        │ 사람·차를 움직인다  │
   └──────────────┘        │ 빈 곳에 건물 채움 │        └────────────────────┘
                           └──────────────────┘
                              1.6MB  →  1.1MB
```

**핵심 원칙: 사진을 한 장도 쓰지 않는다.**
영상의 제작자가 세 번 갈아엎고 도달한 결론과 같습니다.
실사 3D 타일은 눈높이에서 녹아내리고, 국가 3D 지도는 도로가 없습니다.
반면 "좌표 + 규칙"은 어느 거리에서 봐도 형태가 무너지지 않습니다.

## ① 어디서 데이터를 받나

**Overpass API** — OpenStreetMap의 데이터를 조건으로 뽑아 주는 무료 공개 서버.

양재역 사거리(37.484530, 127.034087) 반경 1km 안의 건물·도로·상점·신호등을
**딱 한 번** 요청했습니다. 응답 1.6MB, 3초.

> 무료 공개 서버라 자주 부르면 차단됩니다. 그래서 받은 원본을 디스크에 저장하고
> `--force` 를 주지 않으면 다시 받지 않습니다.
>
> Overpass는 시간 초과나 메모리 부족일 때도 **HTTP 200 으로 "일부만"** 돌려주면서
> `remark` 필드에만 사유를 적습니다. 그걸 그대로 저장하면 지도의 절반이 조용히
> 사라진 채로 작업이 진행됩니다. 그래서 remark를 반드시 검사하고, 건물 300동·
> 도로 200개 미만이면 경고를 띄웁니다.

### 사거리 중심 좌표는 어떻게 정했나

손으로 찍지 않았습니다. OSM에서 **강남대로 상·하행 중심선이 위도 37.48453을
지나는 두 경도**(127.033961, 127.034213)를 계산해 그 중간값을 썼습니다.
남부순환로는 이 지점에서 양재지하차도로 지납니다.

**이 원점은 절대 바꾸면 안 됩니다.** 모든 좌표가 여기 기준 미터이기 때문에,
원점이 바뀌면 이미 만든 것이 전부 어긋납니다.

## ② 파이썬이 하는 일 — "사실"만 다룬다

### 위경도 → 미터

지구는 둥글지만, 몇 km 범위에서는 평면으로 봐도 오차가 0.1% 미만입니다.
위도 37.4845 기준으로 위도 1도 = 110,993m, 경도 1도 = 88,331m 로 환산합니다.

```
x = (경도 - 원점경도) × 88331      (동쪽이 +)
z = -(위도 - 원점위도) × 110993    (북쪽이 -z ← three.js 기본 시선 방향에 맞춤)
```

### 건물 높이 — 절반만 진짜다

| 근거 | 개수 | 비율 |
|---|---:|---:|
| `height` 태그 (실측 높이) | 495 | 54% |
| `building:levels` (층수 × 3.35m) | 512 | 56% |
| 용도·바닥면적으로 추정 | 나머지 | — |

추정 규칙: 아파트 42m, 오피스텔 45m, 사무실 30m, 상업 24m, 주택 7m …
용도도 모르면 바닥면적으로 (120㎡ 미만 9m / 900㎡ 이상 34m).
같은 건물은 언제 만들어도 같은 높이가 나오도록 **id 기반 결정적 난수**를 씁니다.

### 도로 폭 — OSM은 선만 준다

OSM 도로는 굵기 없는 선입니다. 폭은 여기서 만듭니다.

```
폭 = 차로수 × 차로폭
차로수: lanes 태그가 있으면 그것, 없으면 등급별 기본값 × (일방통행이면 1, 아니면 2)
차로폭: 고속 3.6m / 대로 3.4m / 중로 3.3m / 골목 3.0m
보도폭: 대로 3.5m / 중로 3.0m / 골목 2.0m / 이면도로 없음
```

강남대로는 `lanes=8` 이 실제로 붙어 있어 폭 27.2m 가 나옵니다.

### ⭐ 빈 도로변 채우기 — 이 프로젝트에서 가장 큰 판단

양재 일대는 OSM 건물 등록이 성깁니다. **반경 300m 안에 148동뿐**입니다
(영상의 강남역은 770m 구간에 1,191동). 그대로 두면 이가 빠진 도시가 됩니다.

그래서 **도로변을 따라 건물을 만들어 채웁니다.**

```
각 도로를 따라 걸어가며
  ├ 도로 중심에서 (폭/2 + 보도 + 1.2m) 만큼 물러선 선을 잡고
  ├ 정면 폭 8~24m, 안쪽 깊이 11~26m 의 직사각형을 놓아 본다
  ├ 기존 건물·공원·물·다른 도로와 겹치면 → 4m 밀고 다시 시도
  └ 안 겹치면 → 세운다 (도로 등급이 높을수록 높게)
```

결과: 실제 909동 + 생성 1,590동.

> **이건 사실이 아닙니다.** 그래서 화면에 `생성 건물 보이기` 스위치를 뒀습니다.
> 끄면 OSM에 실제로 등록된 것만 남습니다. 어디가 진짜인지 언제든 확인할 수 있어야
> 이 지도를 믿고 쓸 수 있습니다.

### 도로 접면 계산

간판은 아무 벽에나 붙으면 안 됩니다. 건물 외곽선의 각 변마다
"바깥 법선 방향에 도로가 16m 이내에 있는가"를 검사해서 **길에서 보이는 변**만
골라 둡니다. 건물당 평균 1.5개 변이 걸립니다(모퉁이 건물은 2개).

### 상호를 건물에 붙이기

OSM의 가게 이름 1,065개를 가장 가까운 건물(28m 이내)에 붙입니다.
**이때 배열 순서가 아니라 건물 id 로 연결합니다.** 순서로 연결하면 목록이
한 칸만 밀려도 엉뚱한 건물에 엉뚱한 간판이 붙는데, 화면만 봐서는 절대 모릅니다.

### 100m 격자로 자르기

전체를 100m 정사각형으로 잘라 450개 파일로 저장합니다.
도로처럼 격자를 가로지르는 것은 **경계에서 정확히 잘라** 나눕니다
(겹치지도, 비지도 않게 — `tests/verify.py` 가 총 길이가 보존되는지 검사합니다).

이렇게 해 두면 카메라 근처만 읽어서 화면에 올릴 수 있고,
**나중에 범위를 넓혀도 구조를 갈아엎을 필요가 없습니다.**

## ③ 브라우저가 하는 일 — "연출"을 얹는다

### 창문은 그림이 아니라 수식이다

벽 한 장을 만들 때 각 꼭짓점에 **"이 지점이 벽의 가로 몇 m, 높이 몇 m 인가"**를
같이 실어 보냅니다. 그러면 화면의 각 점을 칠하는 프로그램(조각셰이더)이
그 자리에서 계산합니다.

```
층 번호  = 높이 ÷ 층고
열 번호  = 가로 ÷ 창 간격
창 안인가 = 열 안에서의 상대 위치가 창틀 범위인가
불 켜졌나 = 해시(건물번호, 층, 열) < 창문밝기
```

같은 건물의 같은 창은 항상 같은 값이 나오므로, 새로고침해도 야경이 바뀌지 않습니다.

> **여기서 크게 헤맸습니다.** 처음엔 건물 번호를 0~99999 로 넘겼는데,
> 삼각형 위에서 값을 보간할 때 생기는 아주 작은 오차가 해시 안의 `fract()` 를 거치며
> 수백 배로 증폭돼, **창문 하나 안에서 픽셀마다 불이 켜졌다 꺼졌다** 했습니다.
> 화면은 소금·후추를 뿌린 것처럼 보였습니다.
> 건물 번호를 0~1023 으로 줄이자 즉시 사라졌습니다.

### 멀어지면 무늬를 흐린다

창문 하나가 화면에서 1픽셀보다 작아지면 그대로 그릴 때 지글거립니다(모아레).
그래서 **한 화소가 벽에서 몇 m를 덮는지** 계산해 세 단계로 갈아탑니다.

```
가까이  창문 하나하나
중간    창문 4열 × 3층 묶음 (구역마다 밝기가 다름)
멀리    완전 평균
```

한 번에 평균으로 가면 멀리서 건물이 **회색 판자**가 됩니다. 중간 단계가 그걸 막습니다.

> GLSL의 `fwidth()` 로 하는 게 교과서 방법인데, 이 환경에서 쓰레기값을 돌려줘서
> 카메라 거리와 화면 해상도로 직접 계산하도록 바꿨습니다.

### 불빛은 진짜 조명이 아니다

가로등 수백 개를 진짜 광원(PointLight)으로 만들면 프레임이 무너집니다.
그래서:

| 보이는 것 | 실제로는 |
|---|---|
| 창문 불빛 | 스스로 밝은 재질 |
| 가로등 등기구 | 스스로 밝은 상자 |
| 바닥의 빛 웅덩이 | 더하기 합성 판때기(원형 그라디언트) |
| 빛 번짐 | 후처리(블룸) — 밝은 부분만 뽑아 흐려서 다시 더함 |
| 아래층이 따뜻한 것 | 높이에 따라 감쇠하는 색을 벽에 더함 |

**실제 광원은 0개입니다.**

### 간판 — 폰트 파일 없이 글자를 그린다

브라우저에 이미 깔린 시스템 글꼴(맑은 고딕)로 캔버스에 글자를 그려
2048×2048 짜리 큰 그림 한 장(아틀라스)을 만듭니다.
가로 간판 512칸 + 세로 간판 512칸.

간판 밀도는 건물 유형에 따라 다릅니다.

| 유형 | 간판 |
|---|---|
| 저층 상가 | 1~5층 전부 + 모퉁이 세로 간판 |
| 오피스·커튼월 | 1~2층만 + 꼭대기에 건물 이름(OSM 실명) |
| 아파트 | 1층만, 드물게 |

### 사람과 차 — CPU는 아무것도 안 한다

3천 명을 매 프레임 CPU로 움직이면 느려집니다.
그래서 각자에게 **"어느 직선 구간을, 어느 방향으로, 몇 m/s 로"** 만 알려주고
위치·걸음걸이는 GPU가 매 프레임 스스로 계산합니다.

```
걸어간 거리 = (시간 × 속도 + 시작위상) 을 구간 길이로 나눈 나머지
다리 흔들림 = sin(시간 × 속도 × 3.4)
```

### 하루 24시간

`web/src/night/daycycle.js`

태양 위치는 그림이 아니라 **계산**입니다.

```
시간각 H  = (시각 - 12.5) × 15°          ← 12.5 = 서울(동경 127°)의 남중시각
고도      = asin( sin(적위)·sin(위도) + cos(적위)·cos(위도)·cos(H) )
방위각    = acos( (sin(적위) − sin(고도)·sin(위도)) / (cos(고도)·cos(위도)) )
            (오후에는 360° − 방위각)
```

위도 37.4845°(양재), 적위 +5.2°(9월 초)를 넣으면 **일출 06:14 / 일몰 18:46** 이
나옵니다. 실제 서울 9월 9일은 06:05 / 18:49 — 거의 같습니다.

색은 **밤 · 노을 · 낮** 세 벌을 만들어 두고 태양 고도로 섞습니다.

| 고도 | 상태 |
|---|---|
| −9° 아래 | 완전한 밤 (달빛, 별, 가로등 100%) |
| −9° ~ 5° | 노을 — 해 있는 쪽 지평선만 붉어짐, 조명이 켜지기 시작 |
| 5° ~ 17° | 아침·저녁 |
| 17° 위 | 한낮 (파란 하늘, 흰 구름, 조명 꺼짐) |

각 팔레트가 정하는 것: 하늘 위/아래 색, 주광원 색과 세기, 하늘·땅 반사광,
안개 색과 농도, 노출, 블룸 3개 값, 불 켜진 창문 비율, **인공조명 세기(0~1)**.

인공조명 세기(`uArtificial`)가 이 시스템의 핵심입니다.
창문·간판·가로등·빛웅덩이·전조등의 발광이 전부 이 값에 곱해집니다.
그래서 낮에는 자동으로 꺼지고, 해가 지면 저절로 켜집니다.

> 간판은 낮에도 보여야 하므로 다르게 처리합니다.
> `밤에는 스스로 빛나고(uArtificial), 낮에는 햇빛을 받아 보인다(uDayLight)`.

### 거리별로 만드는 양이 다르다 (LOD)

```
카메라에서 260m 이내  건물 + 도로 + 간판 + 가로등 + 가로수 + 사람 + 차
260m ~ 보이는거리     건물 + 도로 + 바닥 빛 웅덩이만
그 밖                 아예 만들지 않음(만들었던 것은 지움)
```

빛 웅덩이만 먼 거리까지 남기는 이유: 위에서 내려다볼 때 도시가 빛나 보이는 건
거의 전부 이것 덕분입니다.

## 검증 — 눈으로 못 잡는 것

`python tests/verify.py` (17개 항목)

- 위경도 ↔ 미터 왕복 오차 < 1mm
- 파이썬과 index.json 의 상수가 일치
- index 에 적힌 청크와 실제 파일이 정확히 일치 (떠도는 파일 0)
- 건물 폴리곤이 전부 반시계 방향 (JS의 바깥 법선 계산이 여기 의존)
- 접면(front) 인덱스가 폴리곤 범위 안
- 건물 무게중심이 실제로 그 청크 안에 있음
- 건물 id 중복 없음 ← **이 검사가 실제로 결함을 잡았습니다**
- 붙은 상호가 그 건물 60m 이내
- **도로를 청크로 자른 뒤 총 길이가 보존됨** (오차 < 1m)
- 명소 좌표가 건물 안에 있지 않음

`node tests/shot.mjs <이름> "<옵션>"` — 크롬을 실제로 띄워 화면을 캡처하고,
콘솔 오류·드로우콜·픽셀 밝기를 함께 뽑습니다. `PROBE="x,y"` 로 특정 화소 색을
숫자로 잽니다("밝아 보인다" 대신 "16%").

## 알려진 한계

1. **높이의 46%는 추정입니다.** 그 자리에 건물이 있다는 건 사실이고, 몇 층인지는 절반만 사실.
